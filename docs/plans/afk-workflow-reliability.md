# Agent workflow 与 Sandcastle AFK 可靠性

状态：2026-09-13 settle 已收敛；[实施计划](afk-workflow-implementation.md)已编写，并完成现有 demo 测试与 skills 仓库完整性检查。执行代码修复与修复后的 AFK 验证尚未开始。

## 目标与约定

一次 `setup-agent-workflow` 配置后，项目能够通过 Sandcastle 执行已约定的 Agent workflow。修改范围由已核实的问题与目标行为决定。

- [项目通过配置接入 AFK](../adr/0002-configure-afk-per-project.md)：复用原生能力，避免每个项目维护专用调度和校验程序。
- [核验通过后合入](../adr/0001-afk-merge-after-verification.md)：定义任务分支与目标分支的交付边界。
- [先试验、后正式使用](../adr/0003-verify-afk-before-formal-projects.md)：定义修复验证与正式项目接入的先后顺序。
- Backlog.md 沿用官方默认：完成时标为终态并提交，任务继续留在 `tasks/` 和看板，定期通过 `cleanup` 收纳至 `completed/`。已完成任务使用 `complete` 收纳；`archive` 用于放弃的任务。收纳后的任务继续通过 ID 查询和解析依赖。
- 继续沿用已约定的停止规则：`held`、`incomplete`、无效结果或无法保全现场时停止 AFK；成功完成后才继续。有效读取且工作耗尽为 `no-work`，仍有工作但不可执行为 `blocked`；父 spec 默认是上下文。

## 调查结论与实施方向

核对对象为本地 Sandcastle fork 与 demo 安装的 0.12.0、Backlog.md 1.51.0，以及 `workflow-e2e-demo` 的源码和既有执行记录。以下结论用于规划修复，不代表修复已经完成。

| 问题 | 方向 |
| --- | --- |
| D10：timeout、abort、completion timeout 后宿主进程可能继续运行 | 修复执行取消与进程终止链路，覆盖失败与提前成功路径。无法确认终止时显式保留执行状态未知，阻止后续合入、清理和分配 |
| D3：多轮返回结果覆盖此前 preserved worktree 路径 | 修复恢复信息累积，兼顾正常结束与后续轮次报错；此前 worktree 未被删除，丢失的是返回值中的定位信息 |
| D9：只以 stdout 完整行判断活动 | 修正活动观测；健康静默工作与真正无进展的执行需要明确的时限语义。子进程存在不能单独证明进展，3600 秒配置只是临时绕过 |
| D1、D2、D4、D5：每轮结果、检查、停走与身份关联 | 围绕合并前核验设计最小通用能力。现有 hooks 只在启动阶段，结果返回前已合并；现有配置不足以满足已约定边界。无需机械地逐项新增 API |
| D6：所需 evidence 随可清理 worktree 消失 | 优先复用持久路径、mount 和现有生命周期能力，补齐实际缺口；验证正常与失败路径的可读取性 |
| D7：prompt 自动发现 | 不作为本次 Sandcastle 缺陷修复；官方模板已显式连接 `promptFile`，setup 应正确复用 |
| D8：默认 `head` | setup 显式配置符合已约定合入边界的执行策略；不预设修改 Sandcastle 全局默认值。Git worktree 与宿主权限隔离是不同概念 |
| Backlog skill 模板 | 区分完成、收纳、放弃；修正直接从 list JSON 读取 `dependencies` 的假设，依照真实 CLI 的 readiness/detail 接口处理 |
| demo 的完成与队列核验 | 修正父 spec 被计入剩余工作、空 artifact 列表可通过、仅凭 commit 对象存在判断持久化等缺口；修复应进入可复用能力与配置规则 |

Sandcastle 的通用执行能力与 workflow 的业务核验规则分别确定。一个新的 hook 只提供检查时点，不会自动生成正确的 tracker、报告、提交和证据核验逻辑。实施规划须给出这些规则的复用方式，并证明项目配置没有重新藏入一套专用执行程序；不预设新增独立 runner 或 package。

## 验收方向

以下均为 required；具体用例、命令、路径和准备工作由后续 ticket 规划与 `acceptance-plan` 绑定。

| 预期结果 | 证明方式 |
| --- | --- |
| 临时新项目从 setup 到连续完成两个真实 AFK 任务，项目仅需必要配置 | 实际 setup 与选定 agent 的完整运行记录；检查生成的项目入口和配置 |
| 已完成任务正确收尾并进入目标分支，后续任务正常开始，队列耗尽时正常结束 | Tracker 状态、目标分支中的提交与报告、证据引用和逐轮执行记录对账 |
| `held` 或终结化核验失败时停止，未通过的工作留在任务分支 | 可控任务结果与临时 Git 仓库验证，观察目标分支和保留现场 |
| 超时或取消后执行确实终止，或终止失败被明确报告并阻断后续动作 | 可控真实进程与后代进程验证；观察返回后的存活与写入行为，不能只断言 Promise 抛错 |
| 所需证据在 worktree 清理后仍可读取；保全失败不会被当成完成 | 临时仓库与故障注入，验证持久 artifact 引用和恢复信息 |
| 合并失败、无效结果和此前轮次的保留现场不会被后续执行掩盖 | 可控故障与多轮结果验证，检查停止行为和恢复引用 |

工程检查沿用各修改仓库的要求，行为证明与 build、typecheck 等工程检查分别记录。新生命周期行为依据上述约定验证；已有行为的保留义务在实施规划中声明并准备必要 baseline。每轮报告记录实际版本、执行环境和证据，未运行的场景保持未验证。

先用可控故障降低真实 agent 试错成本，再在临时新项目验证真实链路。发现问题后修复并重跑受影响场景及完整流程，直到 required 项全部通过且本轮发现的问题处理完；不以任意一次成功覆盖此前未解释的失败，也不据此宣称不存在任何未知缺陷。

修复后的新一轮验证具有新的运行记录；这不改变单次 AFK 遇到 `held` 时停止的规则。正式项目不参与本轮试错，其具体接入属于后续项目工作。用户未要求额外的最终人工批准关卡。
